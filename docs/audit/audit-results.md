# Аудит проекта TG Waitlist

**Дата:** 2026-02-12
**Сценарий нагрузки:** Пост на 300-350к человек, ~20% оставят email (60-70к submissions)
**Инфраструктура:** Vercel (app) + Neon (DB) + Nginx/Traefik proxy (RU-хост)

---

## 1. Анализ готовности к нагрузке

### 1.1. Расчёт пиковой нагрузки

| Параметр | Значение |
|----------|----------|
| Аудитория поста | 300 000 - 350 000 |
| Конверсия в submission | ~20% (60 000 - 70 000) |
| Окно основного трафика | 1-2 часа после публикации |
| Пиковый всплеск | Первые 10-15 минут |
| **Пиковый RPS (оценка)** | **200-500 req/s** |
| Среднее просмотров страницы | ~100 000 - 150 000 |

### 1.2. Vercel (серверные функции)

**Текущие ограничения:**

| План | Concurrent Executions | Bandwidth | Function Duration |
|------|-----------------------|-----------|-------------------|
| Hobby (free) | 10 | 100 GB | 10s |
| Pro | 1 000 | 1 TB | 60s |

**Проблемы:**

- **[КРИТИЧНО] Hobby-план не выдержит нагрузку.** 10 concurrent executions при 200-500 RPS означают мгновенный отказ. Необходим как минимум Pro-план.
- **[ВЫСОКО] Нет конфигурации regions.** По умолчанию serverless functions деплоятся в один регион (iad1 — Washington). Для пользователей через RU-прокси это дополнительная задержка.
- **[СРЕДНЕ] Cold starts.** При всплеске нагрузки множество новых инстансов будут стартовать одновременно, что вызовет задержки в 1-3 секунды.

**Статика (HTML/CSS/JS):**
- Проблем нет — Vercel Edge CDN раздаёт статику с кэшем, выдержит любой объём.

### 1.3. Neon Database (PostgreSQL)

**Проблемы:**

- **[КРИТИЧНО] Отсутствует индекс на `telegram_user_id`.** Каждый запрос на submit делает `SELECT count(*)... WHERE telegram_user_id = ?`. Без индекса это sequential scan. При 60-70к записях запросы будут прогрессивно замедляться.
- **[КРИТИЧНО] Два запроса к БД на каждый submission** (COUNT + INSERT). При 500 RPS это 1000 запросов к БД в секунду. HTTP-драйвер Neon — это отдельный HTTP-запрос на каждый SQL-запрос, то есть 2 HTTP-roundtrip до Neon на каждый submit.
- **[ВЫСОКО] Free-tier Neon не выдержит.** 0.25 vCPU, лимит compute hours. Необходим Scale или Business план с autoscaling.
- **[ВЫСОКО] Race condition при проверке лимита.** COUNT и INSERT не атомарны. При одновременных запросах от одного пользователя можно обойти лимит в 10 записей.
- **[СРЕДНЕ] Нет ограничения на дубликаты.** Один пользователь может записать один и тот же email 10 раз.

### 1.4. Прокси (Nginx + Traefik, RU-хост)

**Проблемы:**

- **[ВЫСОКО] Один контейнер nginx** — единая точка отказа. Нет горизонтального масштабирования, нет реплик.
- **[ВЫСОКО] Не настроено `worker_processes` и `worker_connections`.** Alpine nginx по умолчанию использует 1 worker с 512 connections. При 200-500 RPS через прокси этого недостаточно.
- **[СРЕДНЕ] Буферы прокси консервативны** (`proxy_buffer_size: 16k`, `proxy_buffers: 4 32k`). Достаточно для текущего API, но могут не хватить при задержках от Vercel.
- **[СРЕДНЕ] DNS-зависимость.** Используется `resolver 8.8.8.8` с кэшем 300s. При проблемах с DNS — полная потеря трафика.
- **[НИЗКО] Нет keepalive к upstream.** Каждый запрос через прокси открывает новое TCP-соединение к Vercel.

### 1.5. Вердикт по нагрузке

| Компонент | Готовность | Необходимые действия |
|-----------|------------|----------------------|
| Vercel (статика) | OK | Ничего |
| Vercel (API) | НЕ ГОТОВ | Upgrade до Pro, настроить regions |
| Neon DB | НЕ ГОТОВ | Добавить индекс, upgrade плана, оптимизировать запросы |
| Proxy (Nginx) | ЧАСТИЧНО | Настроить workers, добавить реплики |
| Приложение (код) | НЕ ГОТОВ | Оптимизировать запросы, добавить rate limiting |

## 2. Аудит безопасности

### 2.1. КРИТИЧЕСКИЕ уязвимости

#### VULN-001: Отсутствие верификации Telegram initData

**Файл:** `src/app/api/submit-email/route.ts:12-18`
**Серьёзность:** КРИТИЧЕСКАЯ
**CVSS оценка:** 9.1

**Описание:**
Сервер принимает `telegram_user_id` напрямую из тела запроса без проверки подписи Telegram `initData`. Telegram предоставляет механизм криптографической верификации (`initData` содержит хеш, подписанный токеном бота), но он не используется.

**Вектор атаки:**
```bash
# Любой может отправить запрос с произвольным telegram_user_id
curl -X POST https://target.vercel.app/api/submit-email \
  -H "Content-Type: application/json" \
  -d '{"telegram_user_id": 123456789, "email": "spam@test.com"}'
```

**Последствия:**
- Спам базы данных миллионами поддельных записей
- Заполнение квоты реальных пользователей (10 записей на user_id)
- Подмена email для существующих пользователей
- Полная потеря доверия к собранным данным

---

#### VULN-002: Race condition при проверке лимита записей

**Файл:** `src/app/api/submit-email/route.ts:37-55`
**Серьёзность:** КРИТИЧЕСКАЯ
**CVSS оценка:** 7.5

**Описание:**
Проверка количества записей (COUNT) и вставка (INSERT) выполняются как два отдельных запроса. При одновременных запросах возможен time-of-check to time-of-use (TOCTOU) race condition.

**Вектор атаки:**
```
Запрос A: SELECT count(*) → 9 (OK, < 10)
Запрос B: SELECT count(*) → 9 (OK, < 10)
Запрос A: INSERT → 10 записей
Запрос B: INSERT → 11 записей (лимит обойдён)
```

При достаточном количестве параллельных запросов можно обойти лимит многократно.

**Последствия:**
- Обход бизнес-правила (10 записей на пользователя)
- Спам базы данных

---

#### VULN-003: Отсутствие rate limiting

**Файл:** `src/app/api/submit-email/route.ts` (весь эндпоинт)
**Серьёзность:** КРИТИЧЕСКАЯ
**CVSS оценка:** 8.6

**Описание:**
Эндпоинт не имеет никакого ограничения по частоте запросов — ни по IP, ни глобально. Единственное ограничение — 10 записей на `telegram_user_id`, но это легко обойти, подставляя разные ID (см. VULN-001).

**Вектор атаки:**
```bash
# Простой цикл может заполнить базу тысячами записей
for i in $(seq 1 100000); do
  curl -s -X POST https://target.vercel.app/api/submit-email \
    -H "Content-Type: application/json" \
    -d "{\"telegram_user_id\": $i, \"email\": \"spam$i@test.com\"}" &
done
```

**Последствия:**
- Исчерпание лимитов Vercel (429/503 для реальных пользователей)
- Раздувание базы данных (рост стоимости Neon)
- DDoS на serverless функции
- Полная недоступность сервиса во время атаки

### 2.2. ВЫСОКИЕ уязвимости

#### VULN-004: Отсутствие CORS-ограничений

**Файл:** `src/app/api/submit-email/route.ts`, `next.config.ts`
**Серьёзность:** ВЫСОКАЯ

**Описание:**
API-эндпоинт не устанавливает заголовки CORS и не проверяет `Origin`. Запросы принимаются с любого домена.

**Последствия:**
- Эндпоинт можно вызвать с любого сайта
- Возможна автоматизированная атака с подставных страниц
- Нет контроля над источником запросов

---

#### VULN-005: Отсутствие уникального ограничения на (telegram_user_id, email)

**Файл:** `src/db/schema.ts`
**Серьёзность:** ВЫСОКАЯ

**Описание:**
В схеме БД нет уникального индекса на комбинацию `(telegram_user_id, email)`. Один пользователь может отправить один и тот же email 10 раз, заполняя свою квоту дублями.

**Последствия:**
- Мусорные данные в БД
- Пользователь может случайно заполнить квоту повторными отправками
- Бесполезные записи занимают место

---

#### VULN-006: Отсутствие валидации Content-Type

**Файл:** `src/app/api/submit-email/route.ts:11`
**Серьёзность:** ВЫСОКАЯ

**Описание:**
Сервер вызывает `request.json()` без проверки заголовка `Content-Type`. При некорректном Content-Type парсинг может вести себя непредсказуемо, а ошибка попадает в общий catch блок с 500-ответом.

---

#### VULN-007: Отсутствие ограничения размера тела запроса

**Файл:** `src/app/api/submit-email/route.ts`, `next.config.ts`
**Серьёзность:** ВЫСОКАЯ

**Описание:**
Нет явного ограничения на размер request body. Next.js имеет дефолтный лимит (4MB), но этого достаточно для атаки "large payload" — отправка огромных JSON-объектов для потребления памяти и CPU на парсинг.

**Последствия:**
- Потребление памяти serverless-функций
- Замедление обработки запросов

---

### 2.3. СРЕДНИЕ уязвимости

#### VULN-008: Утечка информации через сообщения об ошибках

**Файл:** `src/app/api/submit-email/route.ts:14-16, 43-44`
**Серьёзность:** СРЕДНЯЯ

**Описание:**
Ошибки содержат детальную информацию о валидации:
- `"telegram_user_id is required and must be a positive number"` — раскрывает имя поля и тип
- `"Maximum number of email entries reached (10)"` — раскрывает точный лимит

Эта информация помогает атакующему подбирать правильный формат запросов.

---

#### VULN-009: Отсутствие Security Headers

**Файл:** `next.config.ts`, `src/app/layout.tsx`
**Серьёзность:** СРЕДНЯЯ

**Описание:**
Приложение не устанавливает защитные HTTP-заголовки:
- `Content-Security-Policy` — нет защиты от XSS
- `X-Content-Type-Options` — нет защиты от MIME sniffing
- `X-Frame-Options` — нет защиты от clickjacking (хотя Telegram WebApp и так в iframe)
- `Strict-Transport-Security` — нет принуждения HTTPS
- `Referrer-Policy` — нет контроля утечки Referrer

---

#### VULN-010: Прокси пропускает все заголовки без фильтрации

**Файл:** `deploy/proxy/docker-compose.yml:41-44`
**Серьёзность:** СРЕДНЯЯ

**Описание:**
Nginx-прокси передаёт все заголовки клиента к Vercel. Нет фильтрации или санитизации. Потенциально позволяет:
- Header injection
- Подмену `X-Forwarded-For` для обхода IP-based ограничений
- Передача вредоносных заголовков к backend

---

#### VULN-011: Отсутствие мониторинга и алертов

**Серьёзность:** СРЕДНЯЯ

**Описание:**
Нет системы мониторинга:
- Нет отслеживания error rate
- Нет алертов на аномальный трафик
- Нет метрик latency
- Нет health check эндпоинта
- Невозможно обнаружить атаку в реальном времени

---

### 2.4. НИЗКИЕ уязвимости

#### VULN-012: Логирование ошибок в console

**Файл:** `src/app/api/submit-email/route.ts:59`
**Серьёзность:** НИЗКАЯ

**Описание:**
`console.error("Failed to submit email:", error)` логирует полный объект ошибки, который может содержать:
- Stack trace с путями к файлам
- Строку подключения к БД (при ошибках подключения)
- Внутренние детали Drizzle ORM

Эти данные видны в логах Vercel и могут быть доступны всем участникам проекта.

---

#### VULN-013: DNS-зависимость прокси

**Файл:** `deploy/proxy/docker-compose.yml:35`
**Серьёзность:** НИЗКАЯ

**Описание:**
Прокси использует `resolver 8.8.8.8 1.1.1.0` (Google DNS + Cloudflare). При блокировке этих DNS в РФ — полная потеря работоспособности прокси.

---

#### VULN-014: Нет проверки на disposable email адреса

**Серьёзность:** НИЗКАЯ

**Описание:**
Принимаются любые email-адреса, включая одноразовые (tempmail, guerrillamail и т.д.). Для waitlist-формы это снижает качество данных.

## 4. Оценка рисков для сценария запуска

### Сценарий: Пост на 300-350к человек

**Без исправлений:**

| Риск | Вероятность | Последствия |
|------|-------------|-------------|
| Сервис ляжет от нагрузки | ОЧЕНЬ ВЫСОКАЯ | Потеря всех потенциальных email |
| Атака спамом в БД | ВЫСОКАЯ | Мусорные данные, рост стоимости |
| Исчерпание лимитов Vercel/Neon | ВЫСОКАЯ | 502/503 для реальных пользователей |
| Proxy не справится | СРЕДНЯЯ | Потеря RU-аудитории |
| Компрометация данных | НИЗКАЯ | Утечка email-адресов |

**Общий вердикт: ПРОЕКТ НЕ ГОТОВ К ЗАПУСКУ В ТЕКУЩЕМ СОСТОЯНИИ.**

Необходимо исправить минимум все КРИТИЧЕСКИЕ и ВЫСОКИЕ уязвимости, а также оптимизировать работу с БД перед запуском.
